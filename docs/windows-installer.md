# Windows installer provenance

The installation checks also exposed stale executable version metadata: the Rust GUI package still used `1.0.0-local`, the placeholder normally replaced by the upstream release workflow. EdenLauncher's custom workflow had only updated the frontend/installer version. The GUI Cargo version is now 2.9.1, with an early CI check against the frontend package version and an upgrade check of the installed executable metadata.

EdenLauncher 2.9.1 uses Tauri's `embedBootstrapper` mode. The normal installer supports a Windows machine without WebView2: it runs the embedded, unchanged Microsoft Evergreen bootstrapper when the Runtime is absent. An internet connection is required to obtain the Runtime. `skip` is not enabled. Evergreen remains maintained by Microsoft; no fixed Runtime is shipped.

The build downloads the bootstrapper from Microsoft's [official link](https://go.microsoft.com/fwlink/p/?LinkId=2124703). `.github/scripts/prepare-webview2.ps1` checks HTTPS at every redirect, the Microsoft delivery host, Windows Authenticode status `Valid`, and the Microsoft Corporation signer. It replaces the Tauri cache only after successful verification. The original bytes, SHA-256, Subject, Issuer, timestamp signer, and verification time are retained as build evidence. `.github/scripts/test-windows-installer.ps1` extracts the resulting EXE and checks that its embedded bootstrapper has the same SHA-256 and a valid signature.

The Windows job also checks EXE/MSI installation, a 15-second application process launch, an installer upgrade from the hash-pinned 2.9.0 EXE, uninstallation, and preservation of test files under the default roaming/local application data paths. These process and fixture checks do not establish that interactive OAuth, the in-app update button, or every real player profile works. The evidence records whether WebView2 was already installed. A preinstalled Runtime is never removed merely for this test. A Microsoft Defender custom scan is attempted only if Defender is already available and active; its status is recorded without altering protection settings.

## Investigation of the 2.9.0 report

Report: [ANY.RUN task ef4fd9e2-d307-4f02-9799-50947266dd20](https://app.any.run/tasks/ef4fd9e2-d307-4f02-9799-50947266dd20).

The released 2.9.0 EXE has SHA-256 `7a690d28aff9ca292c5767cb63d3d1c8b6a6c9e726cf66e257b0a54bc605d35c`. Its archive contains the expected NSIS plugins and the launcher; WebView2 was downloaded at installation time rather than embedded. The [Tauri CLI 2.5.0 template](https://github.com/tauri-apps/tauri/blob/tauri-cli-v2.5.0/crates/tauri-bundler/src/bundle/windows/nsis/installer.nsi) explains the Microsoft fwlink, temporary filename, `/silent /install` arguments, Runtime registry checks, and enumeration of uninstall entries to migrate an existing MSI installation.

The extracted Unicode `System.dll` has SHA-256 `8dc562cda7217a3a52db898243de3e2ed68b80e62ddcb8619545ed0b4e7f65a8`, matching Tauri's NSIS 3.08 distribution. Its source ZIP was checked against the bundler's pinned SHA-1 `057e83c7d82462ec394af76c87d06733605543d4`. NSIS extracts plugins into its temporary `$PLUGINSDIR` to perform Windows API calls. The launcher hook additionally uses this plugin for legacy global-installation migration. These known operations are retained, not renamed to evade detection.

The supplied NSISdl documentation describes an HTTP-only downloader. Switching to an embedded, verified bootstrapper removes this old installation-time download path, and also avoids reuse of an unchecked bootstrapper in the build cache. This is a concrete distribution improvement, not proof that the report's certificate warning was caused by NSISdl.

The exact WebView2 executable from that ANY.RUN session was not available. A fresh official download on 2026-10-23 had SHA-256 `f414de01c4680f0bb0694d1ea7803c6968f3a81bf6bad01b89bfc65dce14c2a2`, Authenticode `Valid`, Subject `CN=Microsoft Corporation, O=Microsoft Corporation, L=Redmond, S=Washington, C=US`, Issuer `CN=Microsoft Code Signing PCA 2024, O=Microsoft Corporation, C=US`. It is a different acquisition; equality with the sandbox sample has not been established. The report's specific certificate warning remains unresolved. Sandbox trust-store, certificate-chain/revocation access, or a different downloaded file are hypotheses requiring the original sample and environment evidence.

EdenLauncher itself remains unsigned. That does not explain a separate certificate warning on a Microsoft-signed child executable. No certificate was purchased, no root certificate was added, and no Defender/SmartScreen/certificate checks or updater hash checks were disabled. The update helper's unnecessary process-level `ExecutionPolicy Bypass` option was removed; it still waits for launcher shutdown and runs the hash-checked installer.

Warnings about unsigned launchers, temporary plugins, Runtime setup, installed-software discovery, or a new binary's reputation may remain. The release includes `EdenLauncher_windows-verification.zip` and `SHA256SUMS.txt`; use them for exact build results rather than interpreting this document as proof of a clean third-party sandbox verdict.
