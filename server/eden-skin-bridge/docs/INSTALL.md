# EdenSkinBridge — установка и эксплуатация

EdenSkinBridge позволяет игроку, который вошёл на EdenWorld без лицензии (офлайн-аккаунт),
применить скин из «Мастерской скинов» EdenLauncher. Скин подписывается через SkinsRestorer
(MineSkin) и сохраняется для игрока. Лаунчер никогда не выбирает целевого игрока: цель — UUID
игрока, который подтвердил привязку в игре, будучи авторизованным.

> Ничего из этого не разворачивается автоматически. Все шаги ниже выполняет администратор.
> Начинайте на тестовом сервере или в окно обслуживания.

## Состав

| Файл | Куда ставить | Зачем |
| --- | --- | --- |
| `EdenSkinBridge-Paper-1.0.0.jar` | `plugins/` основного сервера Purpur (один экземпляр) | HTTP API для лаунчера, привязка `/edenstudio`, применение скинов через SkinsRestorer |
| `EdenSkinBridge-Velocity-1.0.0.jar` | `plugins/` **каждого** Velocity-прокси перед этим сервером | Только для сезона с VeloAuth: подписанный ответ «игрок авторизован» |

Не входят в комплект и не должны копироваться в плагины: SkinsRestorer, nLogin, VeloAuth.

Требования:
- Purpur 1.21.11 (проверена компиляция также с API 26.1.2, 26.2, 26.3); Java 21+.
  **SkinsRestorer 15.12.6 сам требует Java 25** — на основном сервере уже Temurin 25.0.4.
- SkinsRestorer 15.12.6 на сервере (и на прокси, если там тоже стоит SR).
- Текущий сезон: nLogin 2.0.24 на сервере. Следующий сезон: VeloAuth `1.6.2-offline.2` на Velocity.

## Текущий сезон (nLogin)

1. Положите `EdenSkinBridge-Paper-1.0.0.jar` в `plugins/` основного сервера.
2. Запустите сервер один раз — появится `plugins/EdenSkinBridge/config.yml`.
3. В `config.yml`: `auth.adapter: nlogin` (или оставьте `auto` — при установленном nLogin он выбирается сам).
4. Velocity-плагин для этого сезона не нужен: проверка идёт через `nLoginAPI.isAuthenticated`
   на сервере (работает и в режиме, где ядро nLogin стоит на прокси).
5. Дополнительно плагин блокирует привязку после запроса второго фактора nLogin, пока не придёт
   событие успешного входа или 2FA. **Эту последовательность событий нужно проверить на тестовом
   сервере с включённой 2FA:** если nLogin не присылает событие после 2FA, привязка будет
   отклоняться до перезахода (безопасный отказ).

## Следующий сезон (VeloAuth на Velocity)

1. На **каждый** Velocity-прокси положите `EdenSkinBridge-Velocity-1.0.0.jar`.
2. Первый запуск создаст `plugins/edenskinbridge/config.properties` со случайным `shared-secret`.
   Используйте **один и тот же** секрет на всех прокси перед сервером (скопируйте файл).
3. В `config.properties`:
   - `auth-adapter=veloauth`;
   - `allowed-servers=main` — имя основного сервера из `velocity.toml` (`[servers]`);
   - `veloauth-supported-versions=1.6.2-offline.2` — другие версии будут отклоняться, пока их API
     не проверен.
4. На основном сервере в `plugins/EdenSkinBridge/config.yml`:
   ```yaml
   auth:
     adapter: proxy
     require-velocity-forwarding: true
   proxy:
     shared-secret: "<тот же base64-секрет>"
     server-name: "main"
   ```
5. Сервер должен принимать игроков только через Velocity modern forwarding
   (`config/paper-global.yml`: `proxies.velocity.enabled: true`, задан `secret`, `online-mode=false`).
   Иначе плагин сообщит «Velocity modern forwarding is disabled» и не будет привязывать игроков.

Как это работает: при `/edenstudio link` сервер отправляет через соединение игрока запрос с
одноразовым nonce. Прокси перехватывает его (клиент его не видит), проверяет в VeloAuth
`isPlayerAuthorized(uuid, ip)` и `hasActiveSession(uuid, ник, ip)` — те же условия, по которым
VeloAuth пускает игрока на сервер, — плюс отсутствие ожидающего TOTP, и отвечает подписью
HMAC-SHA256 с именем сервера и временем. Сервер принимает ответ только для своего nonce, этого
игрока и своего имени, не старше 30 секунд. Сообщения клиента на этом канале прокси отбрасывает.
Методы `authorize`, `addAuthorizedPlayer`, `forceLogin` и данные паролей не используются.

## SkinsRestorer: хранилище и ключ MineSkin

- Если SkinsRestorer стоит **и на прокси, и на сервере**, выбор скина принадлежит прокси. Чтобы
  сервер мог менять скины через API, у SR на сервере должен быть включён `server.proxyMode.api`
  и **общая MySQL/PostgreSQL база** с SR на прокси. Без этого `/v1/health` покажет
  `skins.ready=false` с объяснением, а применение будет отклоняться (без «ложного успеха»).
- Если SR стоит только на сервере — достаточно его собственного хранилища.
- Генерация подписи идёт через MineSkin средствами SkinsRestorer. Ключ MineSkin (если нужен)
  задаётся в конфиге SkinsRestorer (`api.mineskinAPIKey`) — EdenSkinBridge ключей не хранит.
  Бесплатный режим MineSkin работает с очередью и лимитами: в лаунчере это видно как
  «в очереди на генерацию», это ещё не применение в игре.
- Скин игрока сохраняется как кастомный скин SR с именем `eden` + 12 hex (хэш UUID) и выбирается
  для игрока. Онлайн-игроку он применяется сразу, офлайн — при следующем входе.

## Публикация API через HTTPS

По умолчанию API слушает `127.0.0.1:8787`. Наружу его открывает только обратный прокси с TLS.
Пример для nginx (заглушки заменить):

```nginx
server {
    listen 443 ssl http2;
    server_name skins.example.org;
    ssl_certificate     /etc/letsencrypt/live/skins.example.org/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/skins.example.org/privkey.pem;

    client_max_body_size 1m;
    location /v1/ {
        proxy_pass http://127.0.0.1:8787;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_read_timeout 30s;
    }
}
```

Пример для Caddy:

```caddy
skins.example.org {
    request_body {
        max_size 1MB
    }
    reverse_proxy /v1/* 127.0.0.1:8787
}
```

- `http.trusted-proxies` должен содержать адрес обратного прокси (обычно `127.0.0.1`), иначе
  ограничения частоты считаются по адресу прокси.
- На хостинге с панелью может понадобиться выделенный порт (allocation) и внешний TLS-прокси.
  Плагин не меняет правила брандмауэра.
- Адрес `https://skins.example.org/` вводится в лаунчере: «Мастерская скинов → Настройки →
  Адрес моста скинов EdenWorld». Лаунчер принимает только HTTPS.

## Проверка

```bash
curl -s https://skins.example.org/v1/health
```

Ожидается JSON вида
`{"service":"eden-skin-bridge","auth":{"adapter":"nlogin","ready":true},"skins":{"ready":true},...}`.
В игре администратор может выполнить `/edenstudio status` (право `edenstudio.admin`).

Сценарий игрока: «Мастерская скинов» → аккаунт «Офлайн» → «Привязать игрока» → лаунчер
показывает код → в игре после входа `/edenstudio link КОД` → в чате нажать «Подтвердить» →
в лаунчере подтвердить ник и UUID → «Применить скин».

## Безопасность

- Код привязки (8 символов, ~40 бит) живёт 5 минут и одноразовый; ответ на опрос требует
  отдельный 256-битный секрет, который знает только лаунчер.
- Подтверждение с двух сторон: игрок в игре (будучи авторизованным) и пользователь лаунчера
  (видит ник и UUID). Повторный ввод кода другим игроком не перехватывает привязку.
- Токен лаунчера — 256 бит, на сервере хранится только SHA-256 (`plugins/EdenSkinBridge/links.json`).
  Не более 5 токенов на игрока, неиспользуемые удаляются через 180 дней. `/edenstudio unlink`
  отзывает все привязки игрока.
- Ограничения частоты: по адресу (старт/опрос/завершение), по игроку (команды, 10 смен скина в час).
- Загрузка: только PNG 64×64 или 64×32 до 512 КБ; размеры проверяются по заголовку до
  декодирования; изображение перекодируется без метаданных.
- Все сетевые и дисковые операции SR выполняются в рабочих потоках (2 потока, очередь 64);
  применение к игроку — в основном потоке сервера.

## Откат и удаление

- Остановите сервер, удалите JAR из `plugins/`. Папка `plugins/EdenSkinBridge/` (конфиг и
  `links.json`) остаётся — при повторной установке привязки сохранятся.
- Скины, уже сохранённые в SkinsRestorer, останутся у игроков. Сбросить скин игрок может
  обычной командой SkinsRestorer (`/skin clear`).
- Чтобы отозвать все привязки сразу, удалите `plugins/EdenSkinBridge/links.json` при
  остановленном сервере.

## Переход на новый сезон

1. Поставьте Velocity-плагин на прокси, задайте общий секрет и `allowed-servers`.
2. На сервере переключите `auth.adapter: proxy` и укажите `proxy.shared-secret` и `proxy.server-name`.
3. Привязки (`links.json`) привязаны к UUID на сервере. Если при переходе на VeloAuth меняются
   UUID игроков (другая схема офлайн-UUID), старые привязки перестанут соответствовать игрокам —
   удалите `links.json`, игроки привяжутся заново.
4. Обновление VeloAuth: новая версия будет отклонена, пока её не добавят в
   `veloauth-supported-versions` после проверки её API (см. контрактный тест
   `RealVeloAuthContractTest`).
